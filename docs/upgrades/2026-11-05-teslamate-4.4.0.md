# TeslaMate 4.0.1 to 4.4.0

The target is upstream stable [TeslaMate 4.4.0](https://github.com/teslamate-org/teslamate/releases/tag/v4.4.0), released 2026-10-23, with the matching TeslaMate Grafana image based on Grafana 13.2.4. Both images support the cluster's ARM64 application nodes and AMD64 development hosts, and are pinned by manifest digest in Compose and Kubernetes. PostgreSQL stays on 17.5 and Mosquitto stays on 2.0.21.

## Changes since 4.0.1

- [4.1.0](https://github.com/teslamate-org/teslamate/releases/tag/v4.1.0) adds opt-in Home Assistant discovery, import checkpoints, charging-phase fixes, and a one-time correction of stored charging energy. Existing charge costs are preserved. [4.1.1](https://github.com/teslamate-org/teslamate/releases/tag/v4.1.1) fixes the MQTT startup regression introduced in 4.1.0.
- [4.2.0](https://github.com/teslamate-org/teslamate/releases/tag/v4.2.0) fixes charging recalculation for unusual DC samples and improves sleep detection when Fleet Telemetry is enabled. Home Assistant discovery moves to the device format and changes several discovered entity conventions.
- [4.3.0](https://github.com/teslamate-org/teslamate/releases/tag/v4.3.0) adds editable vehicle ordering, a historical temperature dashboard, vehicle discovery without restarting, and improvements to dashboard navigation and MQTT reliability.
- [4.4.0](https://github.com/teslamate-org/teslamate/releases/tag/v4.4.0) removes trust in compromised intermediate certificates, restores CA certificates for time-zone downloads, updates Grafana security fixes, prevents odometer values from going backwards when stream and poll samples overlap, improves geofence updates, and expands Visited/Temperature/charging dashboards.

MQTT now publishes an empty value when the car explicitly reports a missing value; topics not yet reported since startup retain their previous values. Odometer updates remain nonempty and nondecreasing during a TeslaMate run. Home Assistant discovery remains opt-in; this deployment does not enable it as part of the version update.

## Database changes and rehearsal

Seven migrations follow the deployed schema version `20260411070212`:

1. Preserve cars with a missing VIN using a legacy marker, then enforce non-null VINs.
2. Add import runs, file checkpoints, and rejection records.
3. Increase charging/geofence cost precision without changing stored costs.
4. Change invalid nonpositive charger phase counts to NULL and add a constraint.
5. Recalculate `charging_processes.charge_energy_used`, preserving existing non-NULL values when no replacement can be calculated and leaving costs unchanged.
6. Align the import-run vehicle foreign key with the existing smallint vehicle IDs.
7. Rename the PostgreSQL `range` enum to `preferred_range` without changing its values.

The charger-phase correction and old energy aggregates cannot be recovered by an automatic down migration. A verified pre-upgrade database archive is the rollback point.

Before merging, restore a fresh cloud archive into a disposable PostgreSQL 17.5 container on a Docker internal network with no published database port. Run only the pinned target image's migration command, with a test encryption key and MQTT disabled:

```sh
bin/teslamate eval 'TeslaMate.Release.migrate()'
```

Override the image entrypoint so this runs migrations without starting vehicle loggers. Do not start a second logger against production credentials.

Compare every original public table's count and sequence state before/after. The migration ledger gains seven entries and the three new import tables start empty. Verify drive IDs, mileage, raw position counts, historical charge costs, and all charging fields other than the two intentional corrections remain unchanged. Check that all seven target migrations are applied and invalid nonpositive charger phase counts are gone. Save only aggregate results; exclude credentials, VINs, and coordinates from logs/Git.

For production, capture these private audit parameters while writers are stopped:

```sql
SELECT max(id) AS positions_max_id FROM positions;
SELECT max(id) AS charges_max_id FROM charges;
SELECT coalesce(array_agg(id ORDER BY id), '{}'::integer[])::text AS completed_drive_ids
FROM drives WHERE end_date IS NOT NULL;
SELECT coalesce(array_agg(id ORDER BY id), '{}'::integer[])::text AS completed_charge_ids
FROM charging_processes WHERE end_date IS NOT NULL;
```

Pass those exact values as psql `-v` variables to [the historical audit SQL](2026-11-05-teslamate-4.4.0-audit.sql) before and after deployment. Its output must match. It fixes completed-record cohorts and raw ID cutoffs so resumed logging cannot add rows to the comparison. It hashes raw charging payloads excluding only `charger_phases`, separately checks the normalized phase values, and hashes completed charging processes excluding only `charge_energy_used`; recorded costs are also checked explicitly. Open processes are excluded from immutable payload comparisons because normal logging can update them after restart. Check new migration versions and invalid phases separately. Live total counts and sequences can advance normally.

## Production procedure

An authenticated cluster operator performs privileged backup and validation steps using their local context. The app workflow retains its namespace-scoped deployment identity. Do not transfer administrator credentials to the former logger host.

1. Prove the candidate on the restored clone and complete PR checks, including the pinned Grafana image's actual secret-file startup and subpath health test.
2. With the candidate ready, stop cloud TeslaMate and Grafana writers, suspend the backup CronJob for the maintenance window, and take a fresh custom-format PostgreSQL archive, checksum, aggregate summary, and cold Grafana archive. Verify them and keep a copy outside the cluster.
3. Merge the checked app PR and let the normal protected-main workflow deploy in `active` mode. It starts the new logger, whose entrypoint waits for PostgreSQL and applies migrations. Allow the existing startup/rollout timeout for the one-time charging recalculation.
4. Verify the running TeslaMate/Grafana image digests, version, seven migrations, unchanged raw history/drive mileage/charge costs, and the expected charge-energy corrections. Confirm trusted private HTTPS, Grafana database health, token decryption/refresh, authenticated MQTT, both vehicle loggers, and normal telemetry updates.
5. Verify the backup CronJob is unsuspended, take a post-upgrade backup, and confirm Blob upload/download integrity. Retain both cold pre-upgrade archives and verified post-upgrade backups.

Use the existing single-replica Recreate strategy. The former Compose stack remains stopped with automatic restarts disabled.

## Rollback

Stop cloud writers before restoring. Preserve a verified archive of the failed/new state for investigation. Restore the pre-upgrade PostgreSQL archive and cold Grafana files into separately prepared target storage, then deploy the previous pinned images through a reviewed main-branch change. Reverting only image tags does not restore corrected charging aggregates or the renamed enum, and Grafana's own SQLite migrations also require its pre-upgrade archive for a reliable downgrade. Data collected after the pre-upgrade archive must be reconciled separately.
